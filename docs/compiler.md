# Duck compiler architecture

The language is `docs/spec.md`; packages and the core library are in `docs/quack.md`. This file says how the compiler is built. Every phase is checked against the **corpus**: `examples/*.duck` plus `packages/*/src/*.duck`. "Done" means the corpus compiles and its `test` blocks pass.

## Pipeline
```
source ─▶ lex ─▶ parse ─▶ resolve ─▶ check ─▶ lower ─▶ MIR ─▶ Cranelift ─┬─▶ JIT: run in this process (run, test, pond, hatch, imprints)
         tokens   AST     modules,   types,    explicit   structured        └─▶ object file + libduck_rt.a ─▶ cc (link) ─▶ native exe (build)
                          names      patterns, RC/control C-like IR
                                     effects,  flow
                                     shapes
```
- **Dependencies.** The compiler and runtime are a Cargo workspace (`duck` and `runtime/` = `duck_rt`). Dependencies are kept few and deliberate: Cranelift (`cranelift-{codegen,frontend,module,jit,object,native}`) and `libc` in the compiler; `libc` and `rustls` (+ `webpki-roots`, TLS) in the runtime.
- **Backend = Cranelift.** `duck run`/`test` compile the program in memory and call its entry point in the compiler's own process: the runtime is the `duck_rt` library linked into `duck`, and the JIT resolves runtime symbols through a table generated by the cargo build script (`rt_symbols()`). No C compiler is involved.
- **`duck build`** (release: Cranelift's `speed` optimizations, no `ensures`) writes an object file whose `main` is the entry point and links it with `libduck_rt.a` (the runtime as a static library: the build script builds it with the profile `rt`, release with `panic = "abort"`, and the compiler embeds it) using the system linker driver `cc` (`DUCK_LINKER` overrides it).

## Runtime ABI (runtime/src is the source of truth; `#[repr(C)]` types in `lib.rs`)
- **Scalars:** `int` → `int64_t` (all arithmetic is checked; overflow calls `duck_panic`), `float` → `double`, `bool` → `bool`, `char` → `uint32_t` (code point).
- **Heap objects** begin with `DuckHeader { _Atomic int64_t rc; uint32_t kind; }`. `duck_retain(p)` / `duck_release(p)` (frees at 0, releasing children). They're atomic because async tasks run on threads.
- **str:** an immutable UTF-8 buffer with a byte length, a cached char count and an `is_ascii` flag. Char indexing is O(1) when ASCII. Interning isn't needed.
- **[T]:** a header plus `len`, `cap` and `elem_size`, with elements stored inline (generic code is monomorphized, so element types are known statically). Copy-on-write: mutating with `rc > 1` copies first. A slice `xs[a..b]` / `[h, ..t]` is a view {base, offset, len} that shares the buffer (O(1)).
- **{K: V}:** an insertion-ordered hash map (an index table plus an entries array), copy-on-write.
- **Tuples and structs:** C-layout structs (aggregates; generated functions pass them by pointer and return them through a result pointer, runtime calls follow the platform C ABI); RC fields are retained and released by generated code. **Enums:** a tagged union. A recursive variant field is boxed automatically (a heap cell with a header).
- **T?** → `{bool some; T val}`. **T!** / **T!E** → `{bool ok; T val; DuckErr err}`, where `DuckErr` is a heap object (message, code, cause, plus an optional typed payload with a type id, so `err(BadUrl(w))` can match after conversion).
- **Closures:** `{fnptr, env*}`, with the env heap-allocated and reference-counted.
- **Value:** a C enum mirroring core `Value`. The compiler generates `to_value`/`from_value` per type.
- **Async:** `async fn` compiles to a normal function plus a thunk. Calling it without `await` creates a `DuckTask` (a thunk run on a pthread pool). `await t` joins. `await (a, b)` / `await [..]` starts everything and then joins all of them. A direct `await f(x)` just calls `f` (no thread).
- **Core library in the runtime:** fs, net (tcp; tls via rustls, verified against the bundled Mozilla roots of `webpki-roots`), time, rand, env, proc, string and collection primitives, float formatting (shortest exact output), and `print`.
- **Panics** (overflow, index out of range, a failed `requires`, an unfilled hole, unwrapping `none`) print `panic: <msg>\n  at file:line:col` and exit 101, unless the thread has a recovery point (`runtime/src/catch.c`: a stack of `sigsetjmp` buffers). Then the panic is recorded and `siglongjmp`s back to it, and nothing in between is cleaned up (owned objects leak).
- **`catch e`** lifts `e` into `dk_catch{k}(env)` returning `T!`, like a closure but capturing by reference (env holds pointers to the captured variables), plus a C thunk. `duck_catch(thunk, env, out)` runs the thunk under a recovery point and returns the panic as an `Err` (`panic: <msg> at <loc>`), or NULL.
- **Cancellation:** `t.cancel()` (`duck_task_cancel`) sets the task's flag and bumps `duck_cancel_pending`. Every user loop starts each iteration with `if duck_cancel_pending != 0 { duck_cancel_check(loc) }` (one load while nothing is cancelled). Blocking calls (sleep, await, accept, recv, send, a subprocess's output) wait in 50 ms slices on task threads and check the flag too. A cancelled task panics "cancelled", and `duck_catch` passes that panic on instead of returning it, so no `catch` keeps a cancelled task alive. `await any ts` (`duck_task_await_any`) waits on a condition variable signalled whenever a task finishes.
- **Task links:** every task thread runs under a recovery point. A panic ends only the task; `await` raises it again in the awaiter (where a `catch` can take it). A task that panicked and is freed without being awaited ends the process with the panic report (unless it was cancelled). Each task keeps the tasks it started; when it ends with a panic, it cancels those still running (Erlang's link).

## Contracts, holes, tests, peek, imprint (codegen)
- `requires` → a check at function entry, in every build. `ensures` → a check at every return in debug and test builds; `old(e)` values are captured at entry.
- `??` → `duck_hole("file:line", "expected T")`. `duck build` (release) refuses a program that still has holes; `run`, `check` and `test` allow them.
- `duck test [path]` builds a test binary with every `test` block (including the dependencies' tests only when `--deps` is given), runs each in a forked child process (so a panic fails one test and the rest keep running), and prints `ok`/`FAIL` lines plus a summary. Exit code 1 on any failure. A directory means its project's `src/lib.duck` or `src/main.duck`; a directory with neither (like `examples/`) is treated as flat: each top-level `.duck` file with `test` blocks is built as its own program (with the directory's `quack.toml` dependencies), run in sorted order under a `== <file>` header, followed by a combined `== N files: P passed, F failed` line.
- `peek e` → prints `[file:line] <source text of e> = <show(value)>` to stderr and returns the value.
- `imprint X = e` → the compiler JIT-compiles a helper program that evaluates `e` (pure functions only) and writes `to_value(e)`. It then embeds the result as a constant. No interpreter is needed.

## Back end as built (mir/, build.rs)
- `mir/progen.rs`: refcount helpers, element ops, derived `Show`/`Eq`/`Ord`/hash/`to_value`/`from_value`, literals, constants. `mir/lower.rs` (+ `lower/pat.rs`): bodies, straight from the AST + side tables; every value is an owned temporary or a borrowed operand, scopes release on every exit. `build.rs`: whole-program generation (the entry point: the test runner or the `main` shim), imprints, and `run`/`build`/`ir`/`test`.
- `mir/clif.rs`: a scalar MIR variable whose address is never taken is a Cranelift SSA variable; aggregates and other variables live in stack slots. Generated functions take aggregates by pointer (copied on entry) and return them through a leading result pointer; runtime calls (and generated functions the runtime calls back: element ops, drops, thunks, tests, the `main` shim) use the platform C ABI: an aggregate of at most 16 bytes travels as one or two register words (on x86-64 an all-float eightbyte in a float register), a bigger result through the struct-return pointer.
- `duck run` and `duck test` run the program in the compiler's process; each test runs in a forked child (the runtime's test runner), imprints are computed in a forked child, `duck pond` runs each input and `duck hatch` each candidate's tests in a forked child (hatch's in a process group killed after its timeout). A flat test directory runs each file as `duck __jit test <file>`.
- Patterns compile to sequential first-match tests (no decision trees). Self tail calls in tail position become loops (`goto dk_tail` in `duck ir`); other recursion stays recursive.
- A struct or enum field whose type contains the type itself by value is boxed.
- Top-level `let`s are lazily initialized globals (initialized at startup, released by the leak-check cleanup).
- `imprint`s are computed at compile time (`build.rs`, `eval_imprints`): the compiler generates a helper program from the same typed program in which each imprint is computed through its constant getter (so imprints may use other imprints and `let`s in any order) and its derived `to_value` tree is written to a records file; the compiler parses it and emits each imprint as a global built from that data at startup out of immortal objects (literal strings, lists, maps, boxes), with no initializer code. A panic while computing one is E0420 at the imprint (with the panic message and location); a cycle through function calls is E0115; a type that isn't `Data` is E0350 (in the checker). Nothing is cached.
- A write through a boxed field (`a.boss.pay += 1`, `a.b.c.v = 1`) first makes each box on the path unique (copy-on-write, like lists and maps).
- `ensures` (debug builds): the function becomes a wrapper around the clause group's body. The wrapper finds the clause that matches (pattern tests and pure guards, in order), binds its names, captures the header's and that clause's `old(e)` values, calls the body and checks those `ensures`. Self tail calls stay loops inside the body; the wrapper checks the outer call's result.
- **Execution traces** (`duck run --trace=json|<file>`, `duck test --trace=json|<dir>`, `--trace-limit N`, `--trace-core`; runtime/src/trace.rs). A codegen flag (`progen::Trace`): without it the generated program is unchanged. With it, every Duck function outside core (with `--trace-core`, core's too) is emitted as `<name>_untraced` plus a wrapper `<name>` that records a `call` event with the arguments shown (debug `Show`), calls it, and records `ret` with the shown value, or `err` for a `T!` that failed; every direct call to a traced function first sets the runtime's thread-local trace site (its call site, through `duck__trace_site_slot`), and `main` calls `duck_trace_init`. Self tail calls stay loops inside `_untraced`, so a tail-recursive loop is one call/ret pair. The runtime adds `peek` events (`duck_peek`), `panic` (`duck_panic`) and `signal` (a crash handler on an alternate stack, so a stack overflow still writes its trace), and the test runner a `test` event per test. Events, one JSON object per line:
  `{"ev":"call","fn":"calc.eval","loc":"calc.duck:66:30","args":["Lit(2.0)"],"depth":3}` (`loc`: the call site, or the definition when called through a function value), `{"ev":"ret","fn":"calc.eval","value":"2.0","depth":3}`, `{"ev":"err","fn":"calc.eval","error":"DivZero","depth":3}`, `{"ev":"peek","loc":"f.duck:5","expr":"x * 2","value":"84","depth":1}`, `{"ev":"panic","msg":"...","loc":"f.duck:3:36","depth":4}`, `{"ev":"signal","signal":11}`, `{"ev":"test","name":"t","result":"ok"|"FAIL"}`, `{"ev":"truncated","limit":10000}` (the stream stops after the limit; a final panic/signal is still written) or, at the start of a tail, `{"ev":"truncated","skipped":N}`. Values are cut to 200 chars, and showing one is bounded work (a byte budget in the runtime's string builder stops list/map/str shows early), so a huge argument costs O(1) per call. Nothing is traced while a value is being shown (a user `show`). Configuration reaches the program through the environment (`DUCK_TRACE` = file, directory or `-`; `DUCK_TRACE_LIMIT`; `DUCK_TRACE_TAIL`, default 20): `duck test --trace=json` keeps each test's last events in a ring and the runner prints them under its FAIL line; `duck hatch` does the same (12 events) so a retry prompt shows what the candidate actually did.
- **Task heaps** (runtime/src/heap.rs, copy.rs, chan.rs). Each task allocates into a heap of its own. A tracked object has a 32-byte prefix before its header (a doubly linked list, plus the heap), and `DuckHeader::flags` marks it. The main thread, constant initializers and handles (tasks, connections, listeners, channels) are untracked. Spawn arguments are deep-copied into the new task's heap: generated code switches heaps around per-type copy functions, `Gen::copy_ex` (`DuckElemOps::copy`, `DuckObj::copy` for closure envs and boxes). `await` deep-copies the result into the awaiter's heap. A channel stores an untracked copy of each message and copies it again into the receiver's heap. Handles are shared, and each heap keeps a ledger of the references its task holds on them. When a task crashes, its arguments are dropped (`dk_thunk{i}_drop`) and its heap is swept: every object gets an unreachable reference count and is freed by its kind's free routine, then the handle references still on the ledger are released. When the task is freed, its result is released and the rest is swept. So a crash, a cancellation, or a `catch` inside a task leaves nothing behind. Only a `catch` on the main thread leaks what the aborted code owned. A spawned `async fn` call can't take a `var` argument (E0336); `await f(&x)` runs in place and can.
- **Live reload** (`duck run --live`, src/live.rs). The program is compiled with every call to a user function instance going through a process-wide table: load the slot, `call_indirect`. Slots are keyed by `Program::live_keys` (module file, name and signature, so a key survives edits that renumber instances). A parent process compiles and forks a child to run the program. In the child, a watcher thread polls the source files' mtimes every 200 ms. On a change it re-checks and compiles the whole program into a new JIT module, runs that module's `dk_init` (literals, imprints, constants), and stores the new code addresses into the table. Old modules are never freed. A type error keeps the old code running. If a struct or enum layout changed (`file::Name` → its fields as text), what happens depends on who can hold the type. `live::uses` walks the MIR from the entry point (without entering task thunks) and from each thunk. It collects the user types in every reached function's variables, expanding struct fields and enum variants. Indirect calls reach every closure of the same signature; a closure's body isn't reached just by creating it. If `main`'s side can hold a changed type, the child exits 75 and the parent recompiles and starts a fresh child. Otherwise, the new code is installed and every running task whose thunk (by code address, across all modules so far) can hold one is cancelled (`task::cancel_running`). A task started with exactly one closure, and no other argument that could hold one, records that closure's code address (`DuckTask::hint`; `sup` children are started this way). Its types are then what its thunk reaches without following indirect calls, plus what that closure reaches (computed on demand from the build's call graph). A closure whose environment holds closures falls back to the wide set. Its `sup` supervisor restarts it from scratch on the new code, and nothing else stops. Frames that are already running finish their old bodies, and closures, vtables and element ops keep pointing at the code they were made with. Only the explicit table calls switch.
- `DUCK_LEAK_CHECK=1` makes `duck run` / `duck test` programs fail when runtime objects are still live at exit.

## CLI
`duck run|build|check|test|fmt|explain|pond|lsp|ir|spec`, plus `quack`. `duck ir [--clif] [--trace] <file>` prints the program's MIR as C-like text (`--clif`: the Cranelift IR of every function). `check --json` emits `{file, ok, diagnostics:[{code, severity, line, col, end_line, end_col, message, notes, fixes:[{line, col, end_line, end_col, text}]}]}`.

## Testing
`cargo test` runs the compiler's unit tests plus these integration tests:
- `tests/parse.rs`, `check.rs`, `check2.rs`: the whole corpus parses and checks clean (and its typed program satisfies codegen's invariants); small programs get the exact diagnostic codes, messages and fix-its.
- `tests/run.rs`: every example with a `.out` file runs and matches it (the others run with fixtures from `tests/fixtures/`), every example and package passes `duck test`, leak-checked runs (every package's tests), `duck ir`, codegen edge cases, `duck spec`, and every `tests/errors/*.duck` fails `duck check` with the `// error: E0xxx <message>` in its first line.
- `tests/trace.rs`: execution traces (call/ret nesting, errors through `?`, panics, peeks, the limit, a failing test's trace, valid JSON, an identical program without the flag, leak-free traced builds).
- `tests/units.rs`: units of measure (inference, every unit error, the `3<x` lexing rule, fmt, interpolation, and erasure: the generated program is the same as without units).
- `tests/fmt.rs`, `lsp.rs`, `explain.rs`, `pond.rs`: the formatter (the corpus is fmt-clean), the language server, `duck explain` and the REPL.
- `tests/quack.rs`: the package manager against the registry in `tests/fixtures/registry/`.
- `cargo test -p duck_rt`: the runtime's own unit tests (`runtime/tests/`).
